## 1. Icono adaptativo con fondo blanco

### Problema
El icono de la app mostraba un **contorno verde** en el launcher. Al investigar, los XML adaptativos apuntaban al recurso equivocado:

```xml
<!-- android/app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml -->
<background android:drawable="@drawable/ic_launcher_background"/>
```

Ese `@drawable/` **no** es el color: es un `VectorDrawable` propio con relleno verde `#3DDC84` y una cuadrícula blanca. Por eso cambiar `values/ic_launcher_background.xml` a `#FFFFFF` **no tenía efecto**: ese color nunca se usaba.

### Cambios aplicados

**`android/app/src/main/res/drawable/ic_launcher_background.xml`** — vector verde con cuadrícula → rectángulo blanco sólido:
```xml
<path android:fillColor="#FFFFFF" android:pathData="M0,0h108v108h-108z"/>
```

**`android/app/src/main/res/values/ic_launcher_background.xml`**:
```xml
<color name="ic_launcher_background">#1a6b3c</color>  <!-- antes -->
<color name="ic_launcher_background">#FFFFFF</color>  <!-- ahora -->
```

### Significado
El icono adaptativo de Android (API 26+) tiene dos capas: **background** (fondo) y **foreground** (logo). La capa background se define en un recurso aparte. Al corregir el `drawable`, el fondo blanco ahora se aplica en todas las máscaras (círculo, squircle, cuadrado, teardrop).

### Requisito posterior
Android Studio regenera `mipmap-*/ic_launcher.png` (legacy). Si quieres actualizar el ícono de forma completa, usa **Image Asset** (right-click `res` → New → Image Asset) con fondo `#FFFFFF` y regenera todas las densidades.

## 2. Fix crash `SpillingKt` — Geolocation en Android

### Problema
La app **cerraba sola** al pedir ubicación (diagnóstico de plagas). Logcat:

```
FATAL EXCEPTION: main
java.lang.NoClassDefFoundError: Failed resolution of: Lkotlin/coroutines/jvm/internal/SpillingKt;
    at com.capacitorjs.plugins.geolocation.GeolocationPlugin$getPosition$1.invokeSuspend(GeolocationPlugin.kt:208)
Caused by: java.lang.ClassNotFoundException: Didn't find class "kotlin.coroutines.jvm.internal.SpillingKt"
```

### Causa raíz (3 capas)
1. **Conflicto de versiones Kotlin/Coroutines**: el plugin `@capacitor/geolocation` compilado con Kotlin 1.9 usaba `SpillingKt` (Kotlin 1.9+), pero el proyecto arrastraba una versión de coroutines anterior → clase no encontrada en runtime.
2. **Java 21 vs 17**: `capacitor.build.gradle` generaba `sourceCompatibility JavaVersion.VERSION_21`, incompatible con AGP 8.7.3 y con el runtime Android ≤ API 34 (bytecode 65 no soportado).
3. **Orden de evaluación Gradle**: el `apply from: 'capacitor.build.gradle'` estaba **después** del bloque `android {}`, por lo que su configuración Java 21 pisaba la del proyecto.

### Cambios aplicados

**`android/app/build.gradle`** — orden corregido + Java 17 + versiones forzadas:
```groovy
apply plugin: 'com.android.application'
apply plugin: 'org.jetbrains.kotlin.android'

// 1. PRIMERO: config generada por Capacitor (Java 21 por defecto)
apply from: 'capacitor.build.gradle'

// 2. DESPUÉS: TU config gana (Java 17, kotlinOptions, coroutines)
android {
    namespace = "com.agrilux.app2"
    compileSdk = rootProject.ext.compileSdkVersion

    compileOptions {
        sourceCompatibility JavaVersion.VERSION_17
        targetCompatibility JavaVersion.VERSION_17
    }
    kotlinOptions {
        jvmTarget = '17'
    }
    // ... defaultConfig, signingConfigs, buildTypes ...
}

configurations.all {
    resolutionStrategy {
        force 'org.jetbrains.kotlin:kotlin-stdlib:2.0.21'
        force 'org.jetbrains.kotlin:kotlin-stdlib-jdk8:2.0.21'
        force 'org.jetbrains.kotlin:kotlin-stdlib-jdk7:2.0.21'
        force 'org.jetbrains.kotlinx:kotlinx-coroutines-core-jvm:1.8.1'
        force 'org.jetbrains.kotlinx:kotlinx-coroutines-android:1.8.1'
    }
}
```

**`android/build.gradle`** (raíz) — plugin Kotlin en classpath + Java 17 forzado a todos los módulos:
```groovy
buildscript {
    dependencies {
        classpath 'com.android.tools.build:gradle:8.7.3'
        classpath 'com.google.gms:google-services:4.4.4'
        classpath 'org.jetbrains.kotlin:kotlin-gradle-plugin:2.0.21'   // NUEVO
    }
}

// Fuerza Java 17 en TODOS los módulos (capacitor-android, cordova plugins, etc.)
subprojects {
    afterEvaluate { project ->
        if (project.plugins.hasPlugin('com.android.library') || project.plugins.hasPlugin('com.android.application')) {
            android {
                compileOptions {
                    sourceCompatibility JavaVersion.VERSION_17
                    targetCompatibility JavaVersion.VERSION_17
                }
                // kotlinOptions solo si el plugin Kotlin está presente
                if (project.plugins.hasPlugin('org.jetbrains.kotlin.android')) {
                    kotlinOptions { jvmTarget = '17' }
                }
            }
        }
    }
}
```

**`android/variables.gradle`**:
```groovy
ext {
    minSdkVersion = 24
    compileSdkVersion = 35
    targetSdkVersion = 35
    kotlinVersion = '2.0.21'      // NUEVO
    coroutinesVersion = '1.8.1'   // NUEVO
    // ... resto igual ...
}
```

**`android/app/capacitor.build.gradle`** — Java 17 + kotlinOptions:
```groovy
android {
  compileOptions {
      sourceCompatibility JavaVersion.VERSION_17
      targetCompatibility JavaVersion.VERSION_17
  }
  kotlinOptions { jvmTarget = '17' }
}
```

**`android/capacitor-cordova-android-plugins/build.gradle`**: `VERSION_21` → `VERSION_17`.

### Significado
- **`jvmTarget` vs JDK que ejecuta Gradle** son dos capas distintas. `jvmTarget` define el *bytecode generado*; el JDK configurado en Settings → Gradle JDK es el que *ejecuta* el compilador. AGP 8.7 + Kotlin 2.0 soportan oficialmente **Java 17** como máximo; Java 21/25 son "no soportados" y fallan con `ClassFormatError` o errores de plugin.
- **`force` en `resolutionStrategy`** fija la versión de librerías transitivas, evitando que Gradle resuelva coroutines viejas incompatibles con Kotlin 2.0.21.
- **El orden `apply from:` ANTES de `android {}`** es la clave: el script generado por Capacitor se aplica primero, y tu bloque `android {}` se evalúa después, sobrescribiendo su `compileOptions` (Java 21 → 17).

### Requisito posterior
- **Gradle JDK = JDK 17** en Android Studio → *Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK* → `Eclipse Temurin 17.0.20` (o Microsoft OpenJDK 17).
- **Desde terminal** (Git Bash/WSL) hace falta `JAVA_HOME` apuntando a un JDK 17 o ejecutar Gradle desde Android Studio.

## 3. Fix `androidx.core` 1.17.0 — AAR metadata

### Problema
Al compilar aparecía:
```
4 issues were found when checking AAR metadata:
  1. Dependency 'androidx.core:core:1.17.0' requires ... compile against version 36 or later
     :app is currently compiled against android-35.
  2. Dependency 'androidx.core:core:1.17.0' requires Android Gradle plugin 8.9.1 or higher.
     This build currently uses Android Gradle plugin 8.7.3.
  3. Dependency 'androidx.core:core-ktx:1.17.0' requires ... version 36 or later
  4. Dependency 'androidx.core:core-ktx:1.17.0' requires Android Gradle plugin 8.9.1 or higher.
```

### Causa
Una dependencia transitiva arrastraba `androidx.core:core:1.17.0`, que exige `compileSdk 36` + `AGP 8.9.1+`. El proyecto usa `compileSdk 35` + `AGP 8.7.3`.

### Cambio aplicado (`android/app/build.gradle`)
```groovy
configurations.all {
    resolutionStrategy {
        // ... kotlin / coroutines ...
        // Fix androidx.core 1.17.0 requiring compileSdk 36 + AGP 8.9+
        force 'androidx.core:core:1.15.0'
        force 'androidx.core:core-ktx:1.15.0'
    }
}
```

### Significado
`1.15.0` es la última versión de `androidx.core` totalmente compatible con **AGP 8.7.x + compileSdk 35**. Forzarla evita subir AGP/SDK (que rompería Gradle y el `jvmTarget`).

### Requisito posterior
Ninguno. Solo evita el error de metadata en cada build.

## 5. Cámara nativa con `@capacitor/camera`

### Problema
El botón "Tomar foto" y "Subir foto" **abrían el mismo selector genérico de archivos**. La causa: se usaba HTML5:
```jsx
<input ref={cameraRef} type="file" accept="image/*" multiple capture="environment" onChange={handleFoto} />
```
**Android WebView ignora `capture="environment"`** → siempre abre el file picker genérico.

### Cambios aplicados
**`package.json`**:
```json
"@capacitor/camera": "^8.2.5"
```

**`src/pages/Diagnostico.jsx`** — se reemplaza el `<input type="file">` por llamadas al plugin:
```jsx
import { Camera, CameraSource, CameraResultType } from '@capacitor/camera';

const tomarFoto = async () => {
  const photo = await Camera.getPhoto({
    quality: 80,
    allowEditing: false,
    resultType: CameraResultType.DataUrl,
    source: CameraSource.Camera,      // ← abre la app de cámara nativa
    saveToGallery: true,
    width: 800, height: 800,
  });
  if (photo.dataUrl) setFotos(prev => [...prev, { preview: photo.dataUrl, dataUrl: photo.dataUrl }]);
};

const elegirDeGaleria = async () => {
  const photos = await Camera.pickImages({
    quality: 80, limit: 5, width: 800, height: 800,
  });
  photos.photos.forEach(p => p.webPath && setFotos(prev => [...prev, { preview: p.webPath, dataUrl: p.webPath }]));
};
```

**`capacitor.config.json`**:
```json
"Camera": { "androidPermissions": ["android.permission.CAMERA"] }
```

### Significado
- `CameraSource.Camera` → lanza el intent de la cámara del sistema Android.
- `CameraSource.Photos` / `pickImages()` → selector nativo de imágenes con multi-selección.
- `resultType: DataUrl` → devuelve base64 listo para el `FileReader` manual que usaba el código anterior.

### Requisito posterior
- `npx cap sync android` para registrar el plugin nativo.
- Permiso `CAMERA` en `AndroidManifest.xml` (ya presente).

## 6. Micrófono nativo con `@capacitor-community/speech-recognition`

### Problema
El micrófono **no funcionaba en la app** (sí en web). Logcat:
```
Capacitor/Console: File: - Line 330 - Msg: [object Object]
```
y el error de WebView: `event.error === 'audio-capture'`.

### Causas (3 acumuladas)
1. **Web Speech API no existe en Android WebView.** `window.webkitSpeechRecognition` no está disponible; el API funciona solo en navegadores.
2. **Nombres de métodos incorrectos.** El plugin v7 expone `available()` / `start()` / `stop()`, **no** `isAvailable()` / `startListening()` / `stopListening()`. Con los nombres viejos cada llamada lanzaba excepción y caía al mensaje genérico "No te escuché bien".
3. **Condición de carrera en el import dinámico.** Si el usuario pulsaba el micrófono antes de que terminara `import()`, `SpeechRecognition` seguía en `null` y se mostraba "solo disponible en app nativa".

### Cambios aplicados

**`package.json`**:
```json
"@capacitor-community/speech-recognition": "^7.0.1"
```

**`capacitor.config.json`**:
```json
"SpeechRecognition": {
  "lang": "es-PE",
  "androidPermissions": ["android.permission.RECORD_AUDIO"]
}
```

## 9. Configuración de Git y SSH por clone

### Problemas encontrados
| Síntoma | Causa | Solución |
|---|---|---|
| `fatal: not in a git directory` | Git de **Windows** (MINGW64) sobre ruta UNC de WSL (`//wsl.localhost/...`) — Git for Windows no resuelve `.git` en ese montaje | Usar **git nativo de WSL** para el clone de WSL |
| `Permission denied (publickey)` en WSL | La clave `~/.ssh/id_ed25519` no está registrada en GitHub; la válida es `id_ed25519_lin` | `~/.ssh/config` → `IdentityFile ~/.ssh/id_ed25519_lin` |
| Push pedía contraseña en WSL | Remote usaba `https://github.com/...` | `git remote set-url origin git@github.com:aynitekgroup-code/Agrilux.git` |

### Configuración aplicada (idéntica en ambos clones)
```bash
git config core.autocrlf false    # no convertir LF<->CRLF
git config core.filemode false     # ignorar cambios de permisos
git config core.safecrlf false     # no bloquear por CRLF
git config pull.rebase true        # pull con rebase por defecto
```

**`~/.ssh/config`** (WSL):
```
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_lin
  IdentitiesOnly yes
```

### Significado
- `core.autocrlf=false` + `.gitattributes` = doble barrera contra los saltos de línea.
- `core.filemode=false` = Git ignora el bit de ejecución (Linux sí lo tiene, Windows no).
- `IdentitiesOnly yes` = fuerza a SSH a usar solo esa clave, evitando que intente otras y falle.

### Requisito posterior
**Nunca uses Git de Windows sobre `\\wsl.localhost\...`.**

| Clone | Herramienta Git |
|---|---|
| `C:\Users\...\clon_agrilux_android\Agrilux` | Git de **Windows** (MINGH64 / PowerShell) |
| `~/Lumajira.SAC/Agrilux` | Git **nativo de WSL** (terminal Ubuntu) |

## 10. Espacio en disco

### Problema
El build de Android consumía ~2 GB temporales y el disco C: estaba al 100% (238/238 GB, 257 MB libres).

### De dónde viene
| Qué | Dónde | Tamaño |
|---|---|---|
| Gradle cache | `~/.gradle/caches/` | 500 MB – 1.5 GB |
| Build outputs | `android/app/build/` | 200 – 500 MB |
| Temporales de compilación | `android/app/build/tmp/` | 100 – 300 MB |
| Daemon de Gradle (RAM/swap) | — | 200 – 500 MB |

**El proyecto completo ocupa ~558 MB.** El disco se llenaba por la compilación, no por el código.

### Limpieza aplicada
```bash
# Cache global de Gradle (la más grande)
rm -rf ~/.gradle/caches/

# Build outputs del proyecto
rm -rf android/app/build/
./gradlew clean
```

**En Android Studio:** `Build → Clean Project` · `File → Invalidate Caches / Restart` · `Settings → Gradle → "Delete cached files"`.

**Windows en general:**
```powershell
cleanmgr /sageset:1 ; cleanmgr /sagerun:1   # Liberador de espacio
Remove-Item "C:\Windows\Temp\*" -Recurse -Force -ErrorAction SilentlyContinue
powercfg /hibernate off                        # libera ~tamaño de RAM
```

### Nota sobre Docker (evaluado y descartado)
Se evaluó un entorno Docker para unificar Windows/WSL. **Descartado**:
- Requiere **7–15 GB** (Docker Desktop ~2 GB + Android SDK ~4 GB + Gradle cache ~2 GB) — inviable con el espacio disponible.
- No unifica clones: un contenedor por clone = mismo problema + doble espacio.
- Android Studio necesita el SDK en el host de todos modos.

La solución real fue **`.gitattributes` + config Git (0 MB)**, que ya eliminó los conflictos.
